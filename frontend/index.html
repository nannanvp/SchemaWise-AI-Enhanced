1 Primary keys and entity integrity Keys

The primary key is the column — or the pair of columns — that identifies exactly one row. A table without one cannot be referenced by anything else, which is why the reviewer reports Missing primary key as a warning and drops the score.

  • A table has one primary key. It is implicitly unique and implicitly NOT NULL, so never write those two by hand.
  • Prefer a narrow surrogate key (id INT PRIMARY KEY) over a wide natural key such as an email address — every child table has to store a copy of it.
  • A composite key is correct when the pair really is the identity, for example (student_id, course_id) on an enrolment table.
CREATE TABLE student (
  student_id INT PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL,
  date_of_birth DATE
);
2 Foreign keys and referential integrity Keys

A foreign key is a column that stores another table's primary key. It is what turns two independent lists of rows into a relationship, and it is the constraint the reviewer validates hardest: an invalid reference is reported as an error, not a hint.

  • The referenced column must exist in the same script and must itself be a primary key or UNIQUE.
  • The two types must match — INT to INT, never INT to VARCHAR.
  • Define the parent table before the child that points at it; the reviewer reads one script at a time and cannot see across files.
CREATE TABLE department (
  department_id INT PRIMARY KEY,
  department_name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE student (
  student_id INT PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL,
  department_id INT NOT NULL,
  FOREIGN KEY (department_id) REFERENCES department(department_id)
);
3 NOT NULL, UNIQUE and column rules Constraints

Constraints are the cheapest documentation you will ever write: they are enforced by the database instead of by hope.

  • NOT NULL — a value is required for every row. Ask of each column: "would a missing value be a bug?"
  • UNIQUE — no two rows may share a value. Most engines let several NULLs through anyway, since unknowns are not equal to each other.
  • CHECK — a rule over a value, such as CHECK (marks BETWEEN 0 AND 100).
  • A nullable column is a decision, not a default. The reviewer flags the ones that look accidental.
CREATE TABLE account (
  account_id INT PRIMARY KEY,
  email VARCHAR(150) NOT NULL UNIQUE,
  display_name VARCHAR(80) NOT NULL,
  is_active BOOLEAN NOT NULL
);
4 Normalisation: 1NF to 3NF and BCNF Normalisation

Normalisation removes the redundancy that makes updates dangerous: if the same fact is stored twice, one day only one copy gets corrected.

  • 1NF — one value per cell. A phone_numbers column holding '555-1, 555-2' is not a value, it is a list.
  • 2NF — no non-key column depends on only part of a composite key.
  • 3NF — no non-key column depends on another non-key column. Storing building beside department_id is the classic violation, because the building belongs to the department.
  • BCNF — every determinant is a candidate key. It only bites once a table has several overlapping candidate keys.

The fix is almost always the same: move the dependent facts into their own table and reference it. 

CREATE TABLE department (
  department_id INT PRIMARY KEY,
  department_name VARCHAR(100) NOT NULL UNIQUE,
  building VARCHAR(60) NOT NULL
);

CREATE TABLE lecturer (
  lecturer_id INT PRIMARY KEY,
  lecturer_name VARCHAR(100) NOT NULL,
  department_id INT NOT NULL,
  FOREIGN KEY (department_id) REFERENCES department(department_id)
);
5 Many-to-many needs a junction table Relationships

Two tables can express a relationship directly only when it is one-to-many. Students take many courses, and a course is taken by many students, so neither table can hold the other's key.

  • The junction table's primary key is normally the pair of foreign keys, which also stops the same enrolment being recorded twice.
  • Attributes of the relationship itself — the enrolment date, the grade — belong on the junction table, not on either side.
  • A junction table is also the right place to hang extra keys when a relationship becomes many-to-many over time.
CREATE TABLE student (
  student_id INT PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL
);

CREATE TABLE course (
  course_id INT PRIMARY KEY,
  course_title VARCHAR(120) NOT NULL,
  credit_hours INT NOT NULL
);

CREATE TABLE enrolment (
  student_id INT NOT NULL,
  course_id INT NOT NULL,
  enrolled_on DATE NOT NULL,
  PRIMARY KEY (student_id, course_id),
  FOREIGN KEY (student_id) REFERENCES student(student_id),
  FOREIGN KEY (course_id) REFERENCES course(course_id)
);
6 Naming conventions that survive review Conventions

Names are read far more often than they are written, and the reviewer reads them literally: inconsistent suffixes and reserved words show up as suggestions.

  • snake_case, and singular nouns for tables — student, not Students.
  • The same column keeps the same name everywhere. Pick department_id and use it in every table that references a department.
  • Booleans read as assertions: is_active, has_paid.
  • Avoid reserved words — order, user, group — they need quoting for the rest of the schema's life.
CREATE TABLE customer (
  customer_id INT PRIMARY KEY,
  customer_name VARCHAR(120) NOT NULL
);

CREATE TABLE purchase_order (
  order_id INT PRIMARY KEY,
  placed_on DATE NOT NULL,
  is_paid BOOLEAN NOT NULL,
  customer_id INT NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
);
7 Indexes, joins and foreign-key speed Performance

A foreign key guarantees correctness, not speed. Most engines index the primary key automatically but leave a plain foreign-key column unindexed, so every join and every parent delete scans the child table.

  • Index the columns you join and filter on habitually, not every column that exists.
  • Column order in a composite index matters: (student_id, course_id) serves lookups on student_id alone, but not on course_id alone.
  • Indexes are not free — each one costs space and slows down inserts, updates and deletes.
CREATE TABLE customer (
  customer_id INT PRIMARY KEY,
  customer_name VARCHAR(120) NOT NULL
);

CREATE TABLE invoice (
  invoice_id INT PRIMARY KEY,
  customer_id INT NOT NULL,
  issued_on DATE NOT NULL,
  total DECIMAL(10,2) NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
);

-- the reviewer audits structure, not indexes; add them separately
CREATE INDEX idx_invoice_customer ON invoice (customer_id);
8 Reading a review report Workflow

The report is ranked by severity, and the score is a weighted summary rather than a count. This example is deliberately imperfect — run it and read what comes back.

  • Error something is broken and will fail — an invalid foreign key, for instance.
  • Warning a rule is missing that you will regret later, such as a primary key.
  • Suggestion naming, nullable columns, possible redundancy.
  • Passed a check that succeeded, kept so you can see what was verified.
CREATE TABLE student (
  student_id INT PRIMARY KEY,
  full_name VARCHAR(100),
  department_id INT,
  email VARCHAR(150) UNIQUE
);

Help

Quick start, questions and fixes

Four steps cover the whole application.

  1. Review. Paste CREATE TABLE statements — or press a sample chip — and choose Review Schema. Findings come back ranked, with the score ring filling above them.
  2. Design. In the Table Designer, add columns and tick PK / NN / UQ, or point a foreign key at another table. The SQL writes itself; Send to Review Editor hands it to section I.
  3. Drill. The Quiz asks for a level and a question count, then marks one question at a time. The Exam archive serves tagged past-paper style items — reveal a solution only when you want to see it.
  4. Keep it. Export anything from the Download panel above, and reopen earlier audits from History in the command bar.
Where do I put my Groq API key?

Copy backend\.env.example to backend\.env, set GROQ_API_KEY=… and restart the server — environment variables are read once, at start-up. One key covers every Groq model; there is no separate key per model. Leave it empty and the whole application still works, on the built-in banks.

Which model actually answers?

GROQ_MODEL_PRIMARY is tried first, then GROQ_MODEL_SECONDARY as automatic failover. If both are unavailable the curated offline bank answers instead, and the source on the card reads bank rather than ai.

What does the score measure?

A weighted summary of the audit, not a count of findings: errors cost most, warnings next, suggestions least, and passing checks are recorded without adding points. Two schemas with the same number of findings can therefore score differently.

A foreign key is reported as invalid. Why?

The referenced table must be defined in the same script and the referenced column must be that table's primary key or UNIQUE. Check the spelling on both sides and make sure the data types match.

Why did my history or the leaderboard empty itself?

On a free hosting tier the disk is ephemeral, so every redeploy starts from an empty database. Point the SCHEMAWISE_DB environment variable at a mounted disk to keep it between deploys.

Can I print this, or hand it in?

Yes. Print (Ctrl+P) forces a flat, ink-on-white document at 11pt and removes the application furniture, so the page you are reading becomes the handout. Lessons that are closed stay closed — open them first, or take the Study notes export above.
